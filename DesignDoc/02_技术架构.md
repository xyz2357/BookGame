# 技术架构 / 给 AI 写代码的需求文档

## 总体技术选型

### 实际选择：React + Vite + TypeScript（Web）

> 原文档推荐 Godot 4 / Ren'Py，实际开发选择了 Web 方案。原因：TypeScript 开发速度快、UI 用 HTML/CSS 灵活、部署方便。详见 `07_开发进度与技术实现.md`。

### 曾考虑但未选的方案

- **Godot 4**：好引擎，但对纯文字驱动游戏来说 Web 方案更快
- **Ren'Py**：UI 自定义麻烦
- **Unity**：过重

> 文档以下内容描述系统应该怎么组织，架构设计与引擎无关，实际代码严格遵循。

## 核心系统职责

### GameState（全局状态）

存储一局游戏的全部状态。**整个游戏只有一个 GameState 实例**，所有逻辑读写它。

```
GameState:
    current_node_id: str
    inventory: List[BookInstance]   # BookInstance = {book_id, state}
    flags: Dict[str, any]
    visited_nodes: Set[str]
    triggered_super_matches: List[str]
    key_choices: Dict[str, str]     # choice_id -> chosen_option_id
    
    methods:
        - move_to_node(node_id)
        - add_book(book_id)
        - remove_book(book_id)
        - set_flag(key, value)
        - record_choice(choice_id, option_id)
        - to_save_data() / from_save_data()
```

### EventResolver（事件解析器）

**这是游戏最核心的系统**。给定一个事件 + 玩家选的书，返回一个 Outcome。

```
function resolve_event(event_id, chosen_book_id, game_state) -> Outcome:
    event = load_event(event_id)
    book = load_book(chosen_book_id)
    
    # 1. 检查超级匹配（优先）
    for solution in event.solutions:
        if solution.type == "book_match" and solution.required_book_id == chosen_book_id:
            return solution.outcome  # 大成功
    
    # 2. 检查 tag 匹配
    for solution in event.solutions:
        if solution.type == "tag_match":
            if any(tag in book.tags for tag in solution.required_tags):
                return solution.outcome  # 普通成功
    
    # 3. 没匹配，返回默认结果
    return event.default_outcome
```

**关键细节**：
- 超级匹配 > tag 匹配（顺序很重要）
- tag 匹配默认是 OR（任意一个 tag 命中就算），如果需要 AND 用配置项
- Outcome 的 effects 由 GameState 执行（修改 flags、消耗书等）

### TagMatcher

简单的工具类，提供 tag 集合的匹配判断。MVP 阶段就是 `set.intersection`，未来可扩展（如部分匹配权重等）。

### EndingJudge

章节结束时调用。读取 GameState 的 flags / key_choices / triggered_super_matches，按规则返回结局 ID。

```
function judge_ending(game_state) -> ending_id:
    if game_state.key_choices.get("believed_old_librarian"):
        return "ending_A"
    if "found_lin" in game_state.flags and game_state.key_choices.get("final_choice") == "leave":
        return "ending_B"
    # ...
```

结局规则**完全由数据驱动**——把规则放在 `endings.json` 里，引擎读取，不要硬编码到代码里。这样剧情设计可以随时调整不动代码。

## UI 流程

### 屏幕之间的关系

```
[主菜单] 
   ↓ 开始游戏
[章节开场过场（文字+图）]
   ↓
[节点视图] ←→ [背包视图]
   ↓ 进入事件
[事件视图]
   ↓ 选书 + 解析
[结果反馈]
   ↓ 返回节点视图 或 跳转节点
   ...
[结局视图]
   ↓
[主菜单]
```

### 节点视图（Node View）

显示：
- 当前节点的名称和场景描述（一段文字）
- 节点上未完成的事件列表（点击进入事件视图）
- 可前往的相邻节点列表（点击移动）
- 底部按钮：打开背包

### 事件视图（Event View）

显示：
- 事件描述文本
- 提示："选择一本书来应对" 
- 玩家的背包书列表（可点击选中一本）
- 选中后："使用《XXX》" 按钮，确认后调用 EventResolver
- 显示结果文本，按继续返回节点视图（或跳转）

### 背包视图（Inventory View）

显示：
- 所有书的列表
- 选中一本时，右侧/下方显示这本书的：
  - 标题
  - 作者
  - 一句台词
  - tag 列表
  - 简介
  - 当前状态（normal / worn / glowing）
- 这是**纯查看界面**，不能从这里"使用"书（使用是在事件视图里）

## 数据驱动 vs 代码驱动

**所有内容必须数据驱动**。

- 书、事件、节点、结局规则、UI 文本——全部放进 JSON / 资源文件
- 代码只处理逻辑，不写死内容
- 调整一句台词、加一个事件分支，不需要改代码
- 这样写剧本的人（你自己）可以独立工作，不需要每次都让 AI 改代码

**反例**（不要这样做）：
```python
if event_id == "rusty_door":
    if book_id == "metamorphosis":
        print("你变成虫子钻过去了")
        ...
```

**正例**：所有逻辑通过数据描述，引擎统一解析。

## 存档系统

**已实现**：localStorage 自动存档。

- **自动存档**：每次进入新节点时自动写入 `localStorage`（key: `bookgame_save`）
- **读档**：主菜单检测 localStorage 中是否有存档，有则显示"继续"按钮
- **删档**：到达结局或 game over 时自动删除存档（强制新开局）
- 一个槽位，JSON 格式，包含完整 GameState

```json
{
  "currentNodeId": "main_corridor",
  "inventory": [{"bookId": "metamorphosis", "state": "normal"}, ...],
  "flags": {"met_old_librarian": true},
  "keyChoices": {"mirror_choice": "reach_in"},
  "visitedNodes": ["entrance", "front_room"],
  "triggeredSuperMatches": [],
  "completedEvents": ["e01_dust", "e02_lin_desk"],
  "hp": 3,
  "maxHp": 3
}
```

## PWA 支持

**已实现**：通过 `vite-plugin-pwa` 提供 PWA 能力。

- **离线可用**：Service Worker（Workbox）缓存所有静态资源，包括 Google Fonts
- **可安装**：manifest.webmanifest 定义应用名称、图标、主题色
- **自动更新**：`registerType: 'autoUpdate'`，新版本部署后自动刷新缓存
- **运行时缓存**：Google Fonts CSS 走 stale-while-revalidate，字体文件走 CacheFirst（1 年 TTL）

**已实现**：桌面端和移动端双模式布局。

- **桌面端**（≥768px）：900px 居中容器，NodeView 2 列布局（故事 | 操作），书卡 2 列网格

## 给 AI 写代码时的提示词建议

写需求给 AI 时按这个结构：

1. **先给它读总览** (`00_游戏总览.md`)
2. **告诉它这是数据驱动的游戏，让它优先做数据加载和事件解析器**
3. **每次只让它做一个小系统**（比如"先做 GameState 类"，跑通了再做下一个）
4. **每次写完让它自己写一个最小测试**（构造假数据跑通流程）
5. **遇到不明白的让它问，不要让它瞎猜**

## MVP 开发顺序建议

1. **数据格式定义**（books.json / events.json / nodes.json 的 schema）+ 占位测试数据
2. **GameState** 单类，能创建、修改、序列化
3. **EventResolver** 核心逻辑 + 单元测试
4. **节点移动 + 事件触发**的最简文本流程（命令行也行，先不做 UI）
5. **基础 UI**：节点视图 / 事件视图 / 背包视图（占位美术）
6. **结局判定**
7. **存档**
8. **填真实内容**（这时剧本应该写完了）
9. **美术 + 音效**
10. **测试 + 调整**

**前 4 步是骨架**——做完之后游戏可以"跑"，只是没有内容和 UI。这是关键里程碑。
