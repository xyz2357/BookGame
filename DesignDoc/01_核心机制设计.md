# 核心机制设计

## 玩家有什么

### 1. 背包（Inventory）
玩家持有的所有书的集合。
- 一章 demo 内最多容纳约 10 本书
- 书不会自动消失，但某些事件会消耗或改变书

### 2. 笔记（Journal，可选 V2）
游戏自动记录玩家的关键选择、触发的超级匹配等。
- MVP 阶段可以先不做
- 如果做：用于结局判定的"记忆"系统

## 书（Book）的数据结构

每本书包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 唯一标识，如 `metamorphosis` |
| `title` | string | 显示名，如《变形记》 |
| `author` | string | 作者，如 卡夫卡 |
| `quote` | string | 一句台词（短，<20 字），如 "我必须消失" |
| `tags` | array of strings | 3-5 个 tag |
| `state` | enum | `normal` / `worn`（磨损）/ `glowing`（发光）/ `consumed`（已消耗）|
| `description` | string | 短简介，玩家在背包里查看时显示（1-2 句） |

### 示例

```json
{
  "id": "metamorphosis",
  "title": "变形记",
  "author": "卡夫卡",
  "quote": "我必须消失",
  "tags": ["异化", "甲虫", "家庭", "恐惧", "身体"],
  "state": "normal",
  "description": "格里高尔一觉醒来，变成了一只甲虫。"
}
```

## 事件（Event）的数据结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 唯一标识 |
| `node_id` | string | 所在节点 |
| `description` | string | 事件描述文本 |
| `prompt` | string | 行动提示，如 "选择一本书来应对" |
| `solutions` | array of Solution | 各种解法 |
| `default_outcome` | Outcome | 没有任何匹配时的默认结果 |

### Solution 数据结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `type` | enum | `tag_match` / `book_match`（超级匹配）|
| `required_tags` | array | 如果是 tag_match，需要哪些 tag（任意一个匹配即可，或可设为 AND/OR）|
| `required_book_id` | string | 如果是 book_match，需要哪本书 |
| `outcome` | Outcome | 触发后的结果 |

### Outcome 数据结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `text` | string | 显示给玩家的结果文本 |
| `effects` | array of Effect | 状态改变（消耗书、获得书、设置 flag、跳转节点等）|
| `next_node` | string (optional) | 跳转到哪个节点 |

### Effect 类型

- `gain_book`：获得一本书
- `lose_book`：永久失去一本书
- `mark_book`：改变书的 state（worn / glowing / consumed）
- `set_flag`：设置一个剧情标记，如 `met_old_librarian = true`
- `unlock_node`：解锁某个节点
- `lock_node`：封锁某个节点
- `transform_book`：把一本书变成另一本书（剧情用）

## Tag 系统

### 设计原则

- **不严肃考据**——好用、好匹配比"准确"重要
- **多义性**——同一个 tag 可以从不同书来，事件设计时利用这个
- **覆盖性**——保证每个事件至少有 2-3 种书能解决（不能只有 1 本能解，否则手里没那本就卡死）

### Tag 总池（约 30-40 个）

**情感类**：恐惧、孤独、爱、绝望、希望、愤怒、悲伤、平静

**行动类**：逃避、追寻、毁灭、创造、欺骗、揭露、安慰、拒绝

**身份类**：异化、伪装、双重、纯真、罪、赎罪、流浪、归乡

**意象类**：镜子、画像、甲虫、鬼怪、影子、火、水、门

**世界类**：东方、西方、古典、现代、城市、乡野

**其他**：力量、智慧、知识、记忆、遗忘、时间

> 实际不需要做这么多。MVP 阶段从约 25 个 tag 开始就足够覆盖第一章的所有事件。

## 超级匹配（Super Match）

### 定义

一本特定的书 × 一个特定的事件 = 触发隐藏的特殊结果。

- 不是 tag 匹配，是 book_match（事件指定具体的 book_id）
- 超级匹配优先级 > 普通 tag 匹配（如果两者都满足，以超级匹配为准）

### 设计原则

- 每本书埋 0-2 个超级匹配（不用每本都埋）
- 全章 demo 共埋 4-6 个超级匹配
- **超级匹配应该是"显然合理但不显眼"**——读过书的玩家会笑出来，没读过的也能用普通解法过

## 节点（Node）和地图

### 节点结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | |
| `name` | string | 显示名 |
| `description` | string | 进入时的场景描述 |
| `events` | array of event_id | 节点上的事件 |
| `connections` | array of Connection | 通往其他节点的路径 |

### Connection 结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `target` | node_id | 目标节点 |
| `requirement` | enum | `none` / `tag` / `flag` / `book` |
| `requirement_value` | varies | 比如需要某 tag 的书，或某 flag 为 true |
| `label` | string | 路径显示名，如 "通向后廊" |

### 地图设计

不是网格迷宫，是**有向图**。玩家在节点间移动，部分路径有解锁条件。

具体地图见 `04_关卡内容设计.md`。

## 章节状态机

每章有以下全局状态：

- `current_node`：玩家当前所在节点
- `flags`：剧情标记字典（如 `met_old_librarian: true`）
- `inventory`：背包（书的 id 列表 + 每本的 state）
- `visited_nodes`：已访问节点 set
- `triggered_super_matches`：已触发的超级匹配列表
- `key_choices`：关键节点的选择记录（用于结局判定）
- `completed_events`：已完成事件 set
- `hp` / `max_hp`：当前血量 / 最大血量

## 结局判定

章节结束时，根据以下条件判定结局：

```
if key_choice_1 == "信了老管理员":
    return Ending.A
elif "找到林" in flags and key_choice_3 == "回到地面":
    return Ending.B
elif "找到林" in flags and key_choice_3 == "留下":
    return Ending.C
elif "读完那本书" in triggered_super_matches:
    return Ending.D_隐藏
else:
    return Ending.默认
```

具体结局逻辑见 `04_关卡内容设计.md`。

## 血量系统（HP）

> 原计划 MVP 不做 HP，开发中发现用错书直接卡死体验太差，加入了轻量版本。

- 初始 3 滴血（❤ ❤ ❤），屏幕顶部常驻显示
- **用错书**（无匹配）= 掉 1 血，事件不标记完成，允许换书重试
- **用对书**（tag 或超级匹配）= 不掉血，事件正常完成推进
- **血归零** = 直接进入 game over 结局（"结局：迷失"）

**设计意图**：
- 不是战斗系统，只是对盲目试错的温和惩罚
- 3 次容错空间足够探索，不制造焦虑
- 鼓励玩家阅读书的 tag 和事件描述来推理匹配
